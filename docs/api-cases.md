# API cases: ситуація → метод → статус

Оновлено під специфікацію Етапу 2 і поточний код у `api/` (після спрощення логіки оплати).
Базова адреса: `http://localhost:3000/api/v1`. Усі запити, крім логіну, потребують заголовка `Authorization: Bearer <token>`.

## Позитивні сценарії

| # | Ситуація | Метод і ендпоінт | Статус | Чому | Що ще перевірити |
|---|---|---|---|---|---|
| 1 | Увійти в акаунт з правильним логіном і паролем (`reception` / `Reception123!`) | `POST /auth/login` | 200 | Нічого нового не створюється, сервер просто видає токен | У тілі є `token`, `expires_in` і `user.role`; пароля у відповіді немає; з цим токеном працюють наступні запити |
| 2 | Знайти вільні номери на свої дати для 2 дорослих | `GET /availability?check_in=2026-12-20&check_out=2026-12-23&adults=2` | 200 | Отримуємо список; дати й кількість гостей — це фільтри, тому query | У списку тільки номери, вільні на ці дати, і тільки ті, де вміщаються 2 дорослих |
| 3 | Забронювати вільний номер | `POST /bookings` | 201 | Створюється новий запис про бронювання | У тілі є новий `booking_code` (формат `GCH-РРРР-000000`); статус `confirmed`; дати й номер ті, що ми надіслали; номер зник зі списку вільних (крок 2) |
| 4 | Оплатити бронювання повною сумою | `POST /bookings/:code/payments` (у тілі `amount` і `method`) | 201 | Створюється новий запис про оплату | Сума збігається з `balance_due`; після оплати у `summary` `balance_due = 0`; платіж видно через `GET /bookings/:code/payments` |
| 5 | Скасувати майбутнє бронювання | `POST /bookings/:code/cancel` | 200 | Запис не видаляється, змінюється лише його статус | Статус `cancelled`; є `cancellation.penalty`: 0 для тарифу з `is_refundable = true`, повна вартість номера для `false`; гроші не повертаються (нового платежу немає); номер знову з'явився серед вільних (крок 2) |

## Негативні сценарії

| # | Ситуація | Метод і ендпоінт | Статус | Чому |
|---|---|---|---|---|
| 6 | Забронювати номер, який на ці дати вже заброньований | `POST /bookings` | 409 `ROOM_UNAVAILABLE` | Запиту заважає те, що вже є в базі: інше бронювання на ці дати |
| 7 | Забронювати номер без токена | `POST /bookings` | 401 `UNAUTHORIZED` | Без токена сервер не знає, хто робить запит |
| 8 | Змінити статус номера з токеном рецепції (не admin) | `PATCH /rooms/:id/status` | 403 `FORBIDDEN` | Сервер знає, хто ти, але цю дію може робити тільки admin |
| 9 | Забронювати номер на 3 дорослих, хоча номер розрахований на 2 | `POST /bookings` | 400 `VALIDATION_ERROR` | За специфікацією порушення місткості — це помилка валідації; у `details` буде поле `adults` |
| 10 | Оплатити суму, більшу за залишок до сплати | `POST /bookings/:code/payments` | 400 `VALIDATION_ERROR` | Сума не може перевищувати `balance_due`; у `details` буде поле `amount` |

## Що змінилося порівняно з першою версією

- **№8.** API тільки для персоналу, ролі «гість» немає. Тому замість «скасувати чуже бронювання» перевіряємо роль: рецепція не може робити дію, дозволену лише admin.
- **№9.** Очікуваний статус 400, а не 422: так записано у специфікації. 422 у цьому API означає тільки посилання на запис, якого немає (`REFERENCE_NOT_FOUND`).
- **№10.** Часткова оплата дозволена (сума, менша за вартість, дає 201). Помилкою є тільки сума, більша за залишок.
- **Ендпоінти.** Бронювання визначаються за `booking_code`, скасування і оплата — через `POST /bookings/:code/...`, пошук вільних номерів — через `GET /availability`.
