# API cases: ситуація → метод → статус

## Позитивні сценарії

| # | Ситуація | Метод і ендпоінт | Статус | Чому | Що ще перевірити |
|---|---|---|---|---|---|
| 1 | Увійти в акаунт з правильним email і паролем | `POST /auth/login` | 200 | Нічого нового не створюється, сервер просто видає токен | У тілі є `token`; у відповіді немає пароля; з цим токеном працюють наступні запити |
| 2 | Знайти вільні номери на свої дати для 2 дорослих | `GET /rooms?check_in=2026-12-20&check_out=2026-12-23&adults=2` | 200 | Отримуємо список; дати й кількість гостей — це фільтри, тому query | У списку тільки номери, вільні на ці дати, і тільки ті, де вміщаються 2 дорослих |
| 3 | Забронювати вільний номер | `POST /bookings` | 201 | Створюється новий запис про бронювання | У тілі є новий `id`; дати й номер ті, що ми надіслали; сума = ціна за ніч × кількість ночей; номер зник зі списку вільних (крок 2) |
| 4 | Оплатити своє бронювання повною сумою | `POST /payments` (у тілі `booking_id` і `amount`) | 201 | Створюється новий запис про оплату | Сума збігається із сумою бронювання; статус бронювання змінився на оплачений (перевіряємо через `GET /bookings/:id`) |
| 5 | Скасувати своє майбутнє бронювання | `PATCH /bookings/:id/cancel` | 200 | Запис не видаляється, змінюється лише його статус | У відповіді статус `cancelled`; бронювання досі відкривається через `GET`; номер знову з'явився серед вільних (крок 2) |
